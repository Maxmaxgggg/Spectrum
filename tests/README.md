# Проверка расчёта спектра

Требование к результату абсолютное: для одной и той же матрицы **все** пути
расчёта обязаны давать один и тот же спектр, расхождение даже на единицу —
провал.

## Запуск

```powershell
.\tests\run_tests.ps1
```

Код возврата 0 — всё сошлось, 1 — есть расхождения. При провале печатается
поимённая разница по весам.

Отдельным проектом (`SpectrumTests.vcxproj`), а не режимом основного
приложения: тестовая обвязка не должна попадать в поставляемый бинарник.
Приложение регистрируется как `Alpas/SpectrumTests`, поэтому чекпоинты тестов
не смешиваются с чекпоинтами самой программы.

## Что покрыто

Шесть вычислительных путей — CPU/GPU × простой XOR/код Грея × короткие
(k ≤ 63) / длинные (k ≥ 64) коды, плюс расчёт через дуальный код.

## Откуда берётся эталон

Три независимых источника, и они сверяются друг с другом:

1. **Наивный перебор** (`reference.h`, `bruteForce`) — отдельная тривиальная
   реализация, ничего не переиспользует из `compute/`. Годится до k ≈ 24.
2. **Аналитические весовые перечислители** классических кодов:
   - Хэмминг (7,4) — `1 + 7z³ + 7z⁴ + z⁷`
   - расширенный Хэмминг (8,4) — `1 + 14z⁴ + z⁸`
   - Голей (24,12) — `1 + 759z⁸ + 2576z¹² + 759z¹⁶ + z²⁴`

   Перед прогоном самих алгоритмов тест проверяет, что перебор согласуется
   с аналитикой — иначе эталону нельзя доверять.
3. **Перекрёстная сверка** всех путей между собой на одной матрице.

Для длинных кодов полный перебор невозможен, поэтому эталоном служит
**единичная матрица I(n)**: она порождает вообще все слова, её спектр в
точности равен `C(n, w)`, а при частичном переборе с `maxRows = m` — равен
`C(n, w)` для `w ≤ m` и нулю дальше. Это даёт точный эталон без всякого
перебора.

Спектр снимается сигналом `updateSpectrumPTE` — он несёт точный десятичный
текст. Использовать `updateSpectrumPlot` для сверки нельзя: там `float`, а он
теряет разрядность начиная с 2²⁴.

## Чекпоинты

Сценарий один: посчитать целиком, затем посчитать с прерыванием и
возобновлением — результаты обязаны совпасть точно.

Прерывание задаётся не таймером, а числом операций
(`Worker::setCheckpointOpsPolicy`): момент срабатывания таймера от запуска к
запуску разный, и два прогона было бы не сравнить.

Проверяется:

- обрыв на ~10 / 50 / 90 % пройденного;
- обрыв на границе смены слоя `r` — самое рискованное место для простого XOR;
- несколько сохранений подряд за один проход;
- длинный путь, где полный перебор невозможен;
- **перенос между конфигурациями**: обрыв на одном числе потоков, блоков или
  на одном устройстве, продолжение — на другом.

Последнее существенно. Точка возобновления хранится как абсолютный индекс
(ранг сочетания внутри слоя либо номер маски Грея), а не как номер чанка,
поэтому смена разбиения не должна ни на что влиять. Тест `длинный: CPU -> GPU`
рвётся на 5 168 425 операций при разбиении CPU и продолжается на GPU с совсем
другим — результат обязан сойтись побитово.

## Золотой файл: проверка правок в ядрах

Тестовые матрицы маленькие и «удобные» — на них можно не заметить расхождение,
которое вылезет на объёме. Поэтому для любой правки, затрагивающей сам перебор,
есть отдельная сверка:

```powershell
# до правки
.\tests\x64\Release\SpectrumTests.exe --dump before.txt
# ...правка, пересборка...
.\tests\x64\Release\SpectrumTests.exe --dump after.txt
fc /b before.txt after.txt
```

Прогон занимает около минуты и обрабатывает десятки миллиардов кодовых слов
(самый тяжёлый случай — 80.8 млрд). Матрицы псевдослучайные с фиксированным
зерном и собственным генератором, не зависящим от реализации стандартной
библиотеки, поэтому результат воспроизводится от машины к машине.

В набор входят и контрольные случаи, которые правка ядра коротких кодов
затрагивать не должна: код Грея, дуальный расчёт, длинный путь. И один и тот же
расчёт при двух разных разбиениях (64×256 и 8×64) — результат обязан не зависеть
от числа блоков и нитей.

Эталон лежит в [golden.txt](golden.txt), с ним можно сравниваться напрямую:

```powershell
.\tests\x64\Release\SpectrumTests.exe --dump now.txt
fc /b now.txt tests\golden.txt
```

Пересоздавать `golden.txt` можно **только** осознанно — если изменился состав
случаев. Расхождение при неизменном составе означает, что перебор сломался.

### Выгрузка проверяет себя сама

Сравнение с прошлым прогоном доказывает лишь «ничего не изменилось», но не
«посчитано правильно» — если ошибка была и до правки, диф её не покажет.
Поэтому `--dump` заодно сверяется с теорией и возвращает ненулевой код, если
что-то не сходится:

1. **Число перебранных слов.** Обязано равняться `Σ C(k,r)` для `r = 0..maxRows`
   (либо `2^k` при полном переборе и коде Грея) — это не зависит от содержимого
   матрицы. Ловит потерянные и посчитанные дважды комбинации.
2. **Само распределение.** Для единичных матриц спектр известен точно: `I(n)`
   порождает все слова, поэтому он равен `C(n,w)`, а при частичном переборе —
   `C(n,w)` для `w ≤ maxRows`. Такие случаи сверяются целиком, вплоть до
   `I(50)` с `maxRows=10` — это 13.4 млрд слов.

На случайных матрицах доступна только первая проверка, поэтому в наборе есть и
те, и другие.

Побочное наблюдение: единичная матрица — худший случай по конкуренции за
атомарные операции. Все слова с `r` единицами в маске имеют вес ровно `r`, то
есть весь блок бьёт в одну ячейку общей памяти. `I(50)` считается примерно
вчетверо дольше случайной матрицы того же размера.

## Замеры скорости

`SpectrumTests.exe --bench` — быстрый обзор по четырём случаям.

`SpectrumTests.exe --profile <случай>` — один расчёт и ничего больше, для
сравнения вариантов правки и для профилировщика:

| случай | что нагружает |
|---|---|
| `ident` | вырожденное распределение весов: у `I(n)` весь слой имеет один вес |
| `rand` | то же число комбинаций, но веса размазаны — контроль к `ident` |
| `wide` | строка матрицы в 32 словах: много чтений матрицы на комбинацию |
| `maxshared` | предел по разделяемой памяти: `k=63`, `n=2048` |
| `bigwide` | короткий путь объёмом на десяток секунд, 3.16 млрд комбинаций |
| `biglong` | длинный путь, матрица помещается в разделяемую память |
| `hugelong` | длинный путь, матрица 180 КБ — только глобальная память |
| `graywide` | код Грея на широкой матрице |

**Мерить только на объёме.** На мелких случаях виден не расчёт, а накладные
расходы на запуск ядра, и выводы получаются неверные. Дважды обожглись:
переход на приём Госпера по `--bench` выглядел как +47 % при настоящих 4×, а
перенос матрицы в разделяемую память — как 10 % при настоящих 1.5–2.3×.

**Держать в наборе неизменяемый случай.** Разброс между сборками доходит до
7 %, и без опорной точки его не отличить от эффекта правки. Пока правились
короткие ядра, такой точкой служил `biglong`.

### Ловушка, на которую легко попасться

Тест обязан убедиться, что обрыв **действительно был**. Если расчёт целиком
укладывается в один чанк, цикл проходит один раз, чекпоинт пишется уже по
факту завершения, и «возобновление» просто считает всё заново — сравнение
проходит само собой, ничего не проверив.

Именно так и вышло с первой версией этих тестов: код Грея на Голее (4096
масок) и длинный путь при `maxRows=3` (57 тыс. масок) не прерывались вовсе,
потому что чанк равен 2²⁰ масок. Поэтому `checkResume` сверяет записанное в
чекпоинте число операций с полным объёмом и валит тест, если обрыв не попал
строго внутрь диапазона.

Отсюда выбор данных: для кода Грея — `I(22)` (4.2 млн масок, четыре чанка),
для длинного пути — `maxRows=5` (13 млн) и намеренно мелкое разбиение GPU,
поскольку размер чанка там равен блоки × нити × 4096.

## Автоподбор сетки

При включённой галочке «Подбирать блоки и нити автоматически» перед расчётом
замеряется несколько вариантов сетки на самой матрице, и берётся лучший.
Подбор пишет в отдельный буфер спектра, поэтому на результат он повлиять не
может по построению; тесты это всё равно проверяют.

Что проверяется (`testAutoTunedGrid`, `testAutoTunedCheckpoints`):

- спектр с подбором совпадает со спектром на настройках пользователя — на
  узком и широком коротком коде, на коде Грея и на дуальном;
- отдельно — сверка с аналитикой, а не только «сам с собой»: `I(20)` против
  биномиальных коэффициентов;
- подбор **не** вмешивается на CPU и на длинном пути;
- чекпоинт переносится через подбор в обе стороны: подбор → подбор,
  подбор → фиксированная сетка и обратно. Это существенно: подбор гоняется
  заново при каждом запуске и вполне может выбрать другую сетку, чем в прошлый
  раз, а точка возобновления обязана от разбиения не зависеть.

Тестовые матрицы мелкие, и в боевом режиме подбор на них не запустился бы:
он отказывается работать, если весь расчёт по оценке короче двух секунд. Тесты
снимают порог через `Worker::setGridTuningThreshold(0)` — иначе проверки были
бы пустыми. По той же причине `checkTuned` валит тест, если подбор не
сработал: проверять тогда нечего.

### Насколько он хорош

Качество подбора видно в режиме `--sweep`: он гоняет полный перебор сетки,
находит настоящий оптимум, а затем отдельно замеряет автоподбор.

```powershell
.\tests\x64\Release\SpectrumTests.exe --sweep narrow
```

Полный перебор сетки занимает минуты, поэтому для правок самого подбора есть
быстрый режим — только его таблица замеров и сравнение с настройками:

```powershell
.\tests\x64\Release\SpectrumTests.exe --tune gray
```

| случай | настройки 64x256 | подбор | настоящий оптимум |
|---|---|---|---|
| `narrow` | 5.82 с | 4.08 с (160x256) | 3.59 с |
| `wide` | 7.43 с | 6.10 с (240x128) | 6.04 с |
| `gray` | 2.90 с | 2.90 с (64x256) | 3.04 с |

На коде Грея запаса нет вовсе: умолчание и есть оптимум, и подбор выбирает
ту же сетку.


Список блоков строится от числа мультипроцессоров карты, а не из зашитых
чисел. Случаи специально сделаны крупными: на прежних размерах расчёт
укладывался в сотые доли секунды, и мерить было нечего.

Три грабли, на которые подбор наступал по дороге:

1. **Мерить надо чанком боевого размера.** На уменьшенном куске ядро упирается
   в накладные расходы запуска, и подбор начинает выбирать сетку под них.
   Поэтому размер чанка фиксирован, а под нужную длительность замера
   подстраивается число повторов.
2. **Мерить надо по всему диапазону, а не в одной точке.** У кода Грея номер
   маски — это она сама, и стартовый XOR нити стоит столько строк, сколько
   в маске единиц. В начале диапазона их почти нет; ровно на степени двойки —
   тоже почти нет, и «замер с середины» на 2^34 оказался худшей из возможных
   точек: подбор решал, что лишние нити ничего не стоят. Повторы замера теперь
   разложены по всему диапазону, как идёт и настоящий расчёт.
3. **Подбор сам стоит времени.** Замерено: около трети секунды. На расчёте
   короче десяти секунд это заметная доля, поэтому подбор отказывается
   работать, если по оценке расчёт займёт меньше. Код Грея на 35 строках
   (2.9 с) — как раз такой случай, тем более что умолчание 64x256 на нём и
   так оптимально.

Сетка из настроек пользователя участвует в замере наравне с остальными
кандидатами, поэтому подбор не может оказаться хуже неё: список кандидатов
кратен числу мультипроцессоров, и выставленное вручную значение в него может
не попасть.
